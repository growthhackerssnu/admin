# 데이터 모델 제안 (목업 기준)

기준: main `ecccb28` (2026-09-22, PR #3 병합 시점). 근거는 목업 코드(`prototypes/admin/app.js`, `policy.js`)와 01~04 연동 문서뿐이다. 이전 `prisma/schema.prisma`(Slack 봇 시절 WorkflowRun 기반 스키마)와 별도로 돌던 데이터 구조 초안은 참고하지 않았다. 두 문서 모두 이번 어드민 전환 이전 기준이라 지금 화면과 맞지 않는 부분이 있었기 때문이다.

## 0. 이 문서의 성격

- 01~04 문서가 정의한 화면별 데이터·행동 규격을 실제로 저장하기 위한 **테이블 설계 제안**이다. 확정 스키마가 아니며 DB 담당자 확인 전까지 바뀔 수 있다.
- [backend-mapping.md](../backend-mapping.md)는 이전 세대 스키마(WorkflowRun/RunCompany)를 기준으로 쓰였다. 지금 어드민 방향과 맞지 않는 부분이 있으니, 새 테이블 설계는 이 문서를 기준으로 검토한다.
- 기업을 처음 찾아오는 수집·소싱 파이프라인(뉴스레터 → 기업 후보)은 목업이 구현하지 않는다. "새 기업 탐색" 버튼이 만드는 조건 스냅샷과 비동기 작업만 다루고, 실제 수집 로직(`src/modules/sourcing/*`)과의 연결은 범위 밖이다.
- 확정 정책은 `decisions.md`/`policies.md`/`workflow.md`에 있는 것만 확정으로 표시한다. 나머지는 이 문서의 제안이거나 여전히 미정이다.

## 5. 남은 결정 (백엔드 확인 필요)

- 기업당 진행 중인 outreach를 1개로 강제할지, 차수별 복수 건을 허용할지 ([policies.md:29](../policies.md)).
- `members.role` 권한 범위 — PM만 차수 시작 가능한지, 멤버는 무엇을 못 하는지.
- "논의 중" 이후 다시 리스트업되는 조건 ([workflow.md:38](../workflow.md)).
- "연락 종료"(외부 응답 결과)와 "영구 제외"(내부 결정)의 관계 — 자동으로 영구 제외 처리되는지 ([01:62](01_화면별%20데이터.md)).
- 차수 시작 버튼 클릭 시각을 서버에 어떻게 남기고 동시 시작을 어떻게 처리할지 ([02:26](02_행동별%20연결%20규격.md)).
