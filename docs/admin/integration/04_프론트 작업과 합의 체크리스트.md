# 프론트 준비 작업과 협업 체크리스트

## 현재 코드에서 교체할 부분
| 현재 | 운영 연결 준비 |
|---|---|
| app.js 단일 App + 내부 함수 | 목록/패널/상세/검토/수신자/메시지/응답 컴포넌트 분리 |
| rows 전체를 localStorage 저장 | 행동별 어댑터 호출. DB 전체를 로컬 사본으로 덮어쓰지 않음 |
| patch({...})로 임의 상태 수정 | approveCompany/selectRecipient/saveResponse 등 업무 함수 |
| simulate + 고정 지연 | job 조회와 작업 상태 UI |
| 화면에서 route·발송 가능 여부 판정 | 서버의 상태·allowedActions·blockedReasons 표시, 프론트 검증은 보조 |
| history 문자열 배열 | 구조화된 이벤트 조회·표시 |
| 이름→샘플 이메일 매핑 | contactId/endpointId 기반 선택 |
| Date.now() 샘플 ID | 서버 ID 사용 |
| 담당자·확인자 재욱/PM 고정 | 인증된 사용자·실행자 응답 |
| policy.js 템플릿 null 슬롯 | 템플릿 연결 상태 조회, 생성 요청, 적용 버전 표시 |
| 하나의 busy 플래그 | 작업별 loading/saving/sending 상태 |
| 수정 즉시 ‘저장됨’ | 저장 진행/완료/실패 표시 |

기존 advanceQuarter/flowSteps 같은 미사용 함수와 오래된 설명은 분리 작업 중 제거 대상으로 확인한다. 이번 문서 작성에서는 소스를 수정하지 않았다.

## 권장 코드 구조 (프레임워크 강제 아님)
- screens/: 회사 목록·상세·운영 설정
- components/: 공통 상태·근거·관계자·메시지·이력
- services/outreachRepository: 위 문서의 함수 규격
- services/mockRepository: 샘플 응답과 실패/지연 시나리오
- services/liveRepository: 팀원 API/SDK/RPC 연결
- models/: 요청/응답 타입, 표시용 코드 매핑
- fixtures/: 경로별 샘플, 후보 없음, 미연결, 충돌·오류

샘플과 실제 연결은 같은 인터페이스를 구현한다. 실제 연결 실패 시 몰래 샘플 성공으로 전환하지 않는다. 모드와 실제 발송 여부는 화면에 명확히 표시한다.
React/Vite/TypeScript로 정리할지는 팀의 기존 프로젝트를 확인한 후 결정. 지금 CDN 목업을 반드시 특정 프레임워크로 재작성할 필요는 없다.

## 역할 분담 제안
프론트: 컴포넌트 분리, 입력·검증·로딩·오류·권한 표시, API 어댑터, UI 테스트.
DB/백엔드: 영구 저장, 접근 권한, 동일인/기업 연결, 상태 전환·차수·발송 제한 검증, 이력 원자 저장, 외부 API·작업 실행.
공동: 요청/응답 규격, 상태 코드, 필수 필드, 페이지 방식, 충돌·오류 코드, 차수 시작 시각 의미.
템플릿·노션 담당: 지정 템플릿 원본/버전/변수와 노션 연결 대상 전달. 현재 노션 동기화는 범위 미정.

## 가장 먼저 팀원에게 확인할 10개
- [ ] 기존 DB에서 기업·차수별 컨택 건·관계자·초안을 어떤 ID로 구분하는가?
- [ ] 프론트는 SDK 직접 조회 / RPC / 별도 API 중 어디에 연결하는가?
- [ ] 공유 학회 데이터의 멤버 접근과 PM 권한은 어떻게 제공되는가?
- [ ] 목록 기본 범위·필터·정렬·페이지 규격은 무엇인가?
- [ ] 차수 시작 버튼 시각은 어떻게 기록하며 동시에 시작하면 어떻게 처리하는가?
- [ ] 서버에서 반환하는 상태와 가능한 행동은 무엇인가?
- [ ] 응답 저장 후 보류·거절·담당자 안내·종료는 각각 어디에 노출되는가?
- [ ] 탐색·조사·생성은 즉시 결과인가, jobId 기반인가?
- [ ] 초안 저장·승인 revision과 동시 수정 충돌은 어떻게 처리하는가?
- [ ] 실제 발송 채널·성공 기준·결과 불명 처리와 테스트 모드는 무엇인가?

## 작업 순서와 완료 조건
1. 규격 합의: 위 10개와 핵심 응답 예시를 서로 확인. 테이블 완성까지 기다릴 필요 없음.
2. 어댑터 분리: 샘플 모드에서 현재 화면을 동일하게 시연하고 실제 연결을 쉽게 교체.
3. 조회 연결: 목록/상세/후보/이력, 로딩·빈 결과·오류까지 동작.
4. 저장 연결: 검토·수신자·응답·초안. 새로고침 후 유지되고 다른 팀원 계정에서도 일치.
5. 작업 연결: 템플릿 상태·생성·탐색 작업. 중복 실행 없이 재방문 복구.
6. 실제 발송 연결: 발송 가능 여부·승인 버전·차수 제한·실패/결과 불명 확인 후 별도 단계로 검증.

## 이번 정리의 범위
연동 협의를 위한 문서화만 수행. 실제 Supabase 설정·DB 변경·로그인 구현·프론트 리팩터링은 아직 수행하지 않음. 새 수주 결과 화면이나 노션 동기화를 구현했다고 해석하지 않는다.
