# 기업 수집·사람 검토 파이프라인 작업 목록

기준 브랜치: `feat/dh-pipeline-api` (2026-10-02 원격 main `d408978` 기준). 기존 통합 작업은 `feat/human-review-pipeline`의 `9547628`에 백업했다. 이 PR은 DB·백엔드만 포함하며, 배포된 새 검토 화면과 실데이터 연결은 후속 프론트 PR에서 진행한다. 업무 규칙은 [변경 명세](human-review-db-api-change-spec.md), 테이블별 제안은 [스키마 비교](human-review-schema-comparison.md), API 계약은 [TO-BE YAML](human-review-api-to-be.yaml)을 따른다.

## Gemini 전환 코드 활용 방식

- PR #26으로 main에 들어온 Gemini 전환과 조사 로직을 유지한다. 조사·제안·메시지의 내부 규칙을 최대한 보존하기 위해 이 코드를 기준으로 새 호출 경로를 설계한다.
- 원본의 `gemini.ts`, `companyResearch.ts`, `fitCriteria.ts`, `discoveryAffinity.ts`, `contactResearch.ts`, `fitAssessment.ts`, `outreachDraft.ts`·메시지 생성 라우트·템플릿을 **입력, 프롬프트/판단 규칙, 출력/검증, 다음 작업 호출**로 나누어 비교한다. 사람 검증 흐름으로 바뀌어도 기업 조사 사실·근거 검증, 프로젝트 주제 제안, 메시지 문안·템플릿, 관계자 탐색 기준은 재사용 대상으로 취급한다.
- `gemini.ts`와 의존성은 공용 백엔드에 반영됐고, 옛 `openaiWebSearch.ts`는 제거됐다. 기존 조사 규칙을 새 호출 경로에 연결할 때 현재 Gemini 구현을 재사용한다.
- 자동 fit 판정·자동 연락처 확정·옛 발견 배치 실행처럼 **행동을 결정하거나 작업을 이어 붙이는 부분**만 사람 검증 흐름에 맞춘다. fit 기준은 사람 검토의 판단 자료와 프로젝트 제안 기준으로, 연락처 전략·LinkedIn/공식 도메인 검증은 사람이 관계자를 찾고 확인하는 지원 규칙으로 활용할 수 있는지 검토한다. `discoveryAffinity`의 과거 프로젝트 검색 렌즈는 뉴스레터 기반 수집에 그대로 적용하지 않고 실제 사용 지점을 확인한다.
- 특히 기존 초안 생성은 `FitAssessment.interventions`의 `supportedAreas`를 요구한다. 새 흐름에는 AI fit 결과가 없으므로 저장 조사·사람 판단을 근거로 같은 프로젝트 제안 규칙에 필요한 입력을 마련해야 한다. 메시지 단계의 추가 웹 검색은 허용하지 않는다.
- 기존 튜닝 전후와 새 흐름을 동일 기업 샘플로 비교해 조사 근거, 연락 상대 확인 자료, 프로젝트 주제 3개, 메시지 변수·문안이 보존되는지 검증한다. 시드 변경은 이 비교에 필요한 데이터만 가져온다. 백엔드 PR을 먼저 배포·검증하고 프론트 실데이터 전환은 별도 PR로 진행한다.

### 0단계 조사 결과

- 현재 `Outreach.companyId`는 DB에서 unique다. 사용자가 기업당 메시지 업무 한 건을 확정했으므로 이 제약을 유지한다. 발송 사실은 `SentMessage`로 별도 보존한다.
- 원격 `refactor/db-schema-split`(`1e52518`)은 현재 `main`의 조상이다. 이후 `a5d13c0`에서 대협·HR·포털·재무 백엔드가 `apps/backend`로 통합됐고, PR #26(`887dc1a`)에서 대협 Gemini 전환과 조사 로직 변경이 main에 들어왔다. 현재 브랜치는 두 변경을 모두 포함한다. 새 업무 흐름은 `apps/backend/src/dh`에서 구현한다.
- 새로 수집한 기업과 과거 프로젝트 기업이 모두 같은 회사 레코드로 합쳐질 수 있다. 이미 발송한 기업은 이번 범위에서 새 메시지를 만들지 않고 과거 이력만 조회한다.
- 과거 프로젝트는 있지만 발송 기록과 `Outreach`가 없는 기업은 `Candidate` 없이 `Company`에서 첫 연락 업무를 시작한다. 과거 프로젝트 이력과 사람이 입력한 연락 목적을 생성 근거로 쓰며, 메시지 생성 시 추가 검색하지 않는다.
- 수집원은 사용자가 StartupRecipe로 확정했다. 공식 `startuprecipe.co.kr/archives/invest-newsletter` 아카이브에는 DailyRecipe와 StartupRecipe가 함께 올라온다. 2026-09-28 주간 기사에서 기업명·분야 표 18행 추출을 실제 원문으로 확인했고, 새 파서는 `[StartupRecipe]` 글만 선택한다.
- 제안한 프로젝트의 목표 분기는 `SentMessage.targetQuarterId`로 보존한다. 실제 메시지를 보낸 달력 분기는 `sentAt`을 한국 시간으로 변환해 집계한다. 수주 기업은 별도 확정 기록으로 식별해야 한다. 확정 기록이 없는 기업은 조회 시점의 `수주 미확인`으로 볼 수 있으나 아직 진행 중인 기업을 최종 실패로 분류하지 않도록 집계 시점/마감 규칙을 정해야 한다.
- 사용자 제공 로컬 설정으로 기존 DB를 확인했다. 기존 데이터는 보존하고 `20261001214000_human_review_collection_foundation`, `20261002090000_review_assignment_and_intake`를 적용했다. DB에 이미 적용돼 있던 `20261001090000_add_ghbot_access_tokens`의 마이그레이션 파일은 동료 브랜치에서 복원했다. Prisma 마이그레이션 상태는 최신이다.
- 이전 `align_v04` 마이그레이션은 당시 픽스처를 전제로 업무 데이터를 DELETE했다. 이번 이관에서는 이 패턴을 사용하지 않는다.

**완료 조건:** 새 기업과 기존 기업의 한 건을 각각 데이터 흐름에 넣어도 회사·후보·연락 업무·발송 기록의 수와 관계가 모호하지 않다. 운영 데이터의 보존 위치가 명확하다.

### 1단계 확장(적용 완료)

- `CollectionSource`, `CollectionItem`, `CollectedCompany`, `CompanyNameKey`, `CandidateReviewDecision`과 새 상태 enum을 추가했다. 원문·소스·정규화 기업명의 유니크 제약, 조회 인덱스, FK, RLS 기본 거부가 마이그레이션에 있다.
- 기존 `SearchRun`에는 `sourceId`·`scheduledFor`, 기존 `Candidate`에는 `originCollectedCompanyId`를 nullable로 더했다. 이전 행을 채우거나 바꾸지 않는다. 신규 cron에서는 이 값을 필수로 검사한다.
- 이전 행을 보존하려고 `SearchRun`의 분기·담당자, 후보/조사의 원탐색 참조, 새 상태를 물리적으로 nullable로 열었다. 신규 API는 필요한 값을 경로별로 검사한다. `ResearchTask.pipeline` 기본값은 `legacy`; 구 worker는 새 `human_review` 작업을 선점하지 않는다.
- `Outreach`의 후보·연락 목적·발송 상태, 초안 근거·스냅샷, `SentMessage` 기록자·초안 버전 필드를 nullable로 추가했다. 기존 기업 유니크 제약은 그대로 유지한다.
- `prisma validate`, 백엔드 타입 검사와 두 마이그레이션 적용을 확인했다. 복원 DB 리허설은 별도로 수행하지 않았다.

**완료 조건:** 기존 API가 계속 동작하고 신규 데이터도 저장 가능하다. 과거 프로젝트·판단·발송 행이 보존된다.

## 현재 진행

현 단계의 범위는 신규 리스트업이며 과거 컨택·프로젝트 기업의 신규 업무 흐름은 보류한다. 로컬 백엔드·백업 브랜치 프론트에서 Google 로그인 후 `/me`, 목표 분기, 후보 목록과 운영 현황 API의 200 응답을 확인했다. StartupRecipe 원문 1건에서 18개 후보를 DB에 저장하고 같은 원문 재실행에서 0건 추가를 확인했다. 처음 검토 화면에서는 조사 대기 17건과 오류 1건을 확인했고, 팀장용 배정 화면에서 활성 팀원 조회와 배정 가능 0건에 대한 총량 부족 응답을 확인했다. 2026-10-02 교체된 Gemini 키로 딥엑스 조사 한 건을 실행해 `ResearchTask=succeeded`, 후보 조사 상태 `ready`, 출처 근거가 연결된 `ResearchClaim` 4건을 DB에서 확인했다. 오류 작업의 재시도와 이후 배정·검토·초안·첫 발송 기록의 실데이터 검증은 남아 있다. 로컬 자동 일정은 비활성화했다. 배포된 기본 `/dh`는 새 3열 검토 화면이지만 아직 샘플 데이터를 사용한다. 이 브랜치에서 Prisma 스키마·DB 마이그레이션 상태, 백엔드 타입 검사, 대협 테스트 97개를 확인했다. 생산 빌드는 로컬 네이티브 의존성 경고가 있었지만 Windows ARM 런타임에서 종료 코드 0으로 완료했다.
